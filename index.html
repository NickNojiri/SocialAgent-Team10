SpotBot Capstone Plan

A seven-month build plan for four people. Paste a reel, get a votable spot card, turn a group chat into an actual plan — now with the evidence to prove it works.

14 sprints 4 owners 2 semesters Working prototype → deployed system

The project already has the best capstone hook available: a known but unmeasured quality gate. Capture succeeds somewhere between 40% and 70% of the time and nobody has measured it. Turning that into a measured, improved, defended number is worth more than five new features.

With exactly four people: Nick takes Architecture + Platform (Track D), and the three teammates take A, B, and C. Track D’s security & ethics review pairs naturally with Track B if it needs a home.

The anti-bottleneck rules

Nick built almost all of the existing system and the other three are new to this. Without guardrails the default outcome is one person writing everything — which is both a grading problem and a burnout problem. These are non-negotiable.

  1. Nick reviews; Nick does not implement another track’s code. If someone is stuck more than a day, Nick pairs for 45 minutes — screen shared, they type.
  2. No self-merge. Every PR needs one non-author approval. This forces cross-reading.
  3. Every person demos their own work at the biweekly review. If Nick demos it, it isn’t owned.
  4. Track boundaries are module boundaries. A lives in sources/, B in eval/, C in app/, D in CI and deploy config. Low collision by design.
  5. You must be able to explain any code you ship. AI agents are encouraged; code you can’t explain in review doesn’t merge. This is the rule that protects you at demo day.
Section 02

Week 0 — Bootcamp

The highest-leverage two days of the whole project. Goal: every teammate runs the full stack locally and merges one tiny PR. A beginner who has shipped once behaves completely differently from one who hasn’t.

  • Everyone installs Python 3.11+, Git, Ollama, VS Code
  • Clone → git checkout feature/reel-capture → .\scripts\setup.ps1 (already written)
  • Everyone gets their own Discord bot token plus a shared test server, then runs run_local.ps1
  • Everyone captures one reel and watches their own card appear
  • One tiny PR each — five lines, pre-picked by Nick. Branch → PR → review → merge. The point is the ritual, not the code.
  • Read together: README.md, docs/PIPELINE.md, docs/PRODUCT_ROADMAP.md
  • Agree on sprint cadence, standup channel, definition of done, commit convention
Ships: 4 merged PRs · 4 working environments · docs/TEAM.md charter

Section 08

What to include — and what to skip

Cheap things that score disproportionately well, and expensive things that score nothing.

Include

  • ADRs in docs/adr/ — shows engineering judgment, not just coding
  • A before/after metrics table — the single most persuasive slide you will have
  • A risk register recording what actually went wrong and how you responded
  • Individual contribution statements — protects each of you in grading
  • A 2–3 minute demo video with a recorded fallback. Never live-demo without one.
  • Coverage badge and green CI on the README
  • A security & ethics section — ToS position (user-initiated paste only, never crawling), prompt-injection defense, PII handling, data deletion. Graders reward this and most teams skip it.
  • A public artifact — the OSS repo and the shareable catalog page. Something they can click.

Ask your advisor early

  • Whether the usability study needs IRB review — class projects are often exempt, but ask rather than assume
  • Whether the scraping approach is acceptable or they’d prefer the official Meta API. Have a written answer either way.

Skip deliberately

  • Payments, mobile apps, custom auth systems, microservices, Kubernetes — each eats a sprint and adds nothing to the grade
