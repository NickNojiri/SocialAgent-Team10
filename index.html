The anti-bottleneck rules

Nick built almost all of the existing system and the other three are new to this. Without guardrails the default outcome is one person writing everything — a grading problem and a burnout problem. These are non-negotiable.

  1. Nick reviews; Nick does not implement another track’s code. Stuck more than a day? Nick pairs for 45 minutes — screen shared, they type.
  2. No self-merge. Every PR needs one non-author approval. This forces cross-reading.
  3. Every person demos their own work at review. If Nick demos it, it isn’t owned.
  4. Track boundaries are module boundaries. A lives in sources/ and extractors/, B in eval.py, normalizer.py and the label corpus, C in app/.
  5. You must be able to explain any code you ship. AI agents are encouraged; code you can’t explain in review doesn’t merge. This rule protects you at demo day.
Section 03

Week 0 — Kickoff

Goal: every teammate runs the project on their own laptop, picks a track, and leaves with a first task. A beginner who has shipped once behaves completely differently from one who hasn’t.

  • Before the meeting, at home: install Python 3.11+, Git, VS Code, Ollama, then ollama pull mxbai-embed-large
  • Clone the repo (main) → .\scripts\setup.ps1
  • First run, no Discord token needed: pytest -k "not live" -q, then the eval command — everyone sees the same 37.4%
  • Nick demos the bot live, with a recorded fallback
  • Each person picks a track, then one small first task with a due date
  • Agree on meeting cadence, standup channel, definition of done, PR rules
  • Discord bot tokens and a shared test server wait for Sprint 1 — not day one
Ships: 3 working environments · 3 chosen tracks · 3 first tasks · docs/TEAM.md

Section 09

What to include — and what to skip

Cheap things that score disproportionately well, and expensive things that score nothing.

Include

  • The leakage story, told first — 49.6% → 37.4%, found and fixed, not hidden. Advisors trust the rest of the work more for hearing it up front.
  • A before/after metrics table with intervals — the single most persuasive slide you will have
  • A negative result, written up — the local LLM made extraction worse on CPU, measured twice
  • ADRs in docs/adr/ — engineering judgment, not just code
  • A risk register of what actually went wrong and how you responded
  • Individual contribution statements — protects each of you in grading
  • A 2–3 minute demo video with a recorded fallback
  • A security & ethics section — ToS position (user-initiated paste only, never crawling), prompt injection, PII, data deletion
  • A public artifact — the OSS repo and the shareable catalog page

Ask your advisor early

  • Whether the usability study needs IRB review — often exempt for class projects, but ask
  • Whether the scraping approach is acceptable or they’d prefer the official Meta API
  • Whether a measured heuristic parser counts as the ML contribution, or a trained model is expected

Skip deliberately

  • Payments, mobile apps, custom auth systems, microservices, Kubernetes — each eats a sprint and adds nothing to the grade
